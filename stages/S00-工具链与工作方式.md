# S00 · 工具链与工作方式（16h / 约 4 天）

> **Stage 目标**：能独立启动、调试、提交代码；并且建立「用 AI 学而不是让 AI 代写」的工作方式。
> 这个 Stage 不写游戏逻辑，但决定了后面 20 多周的学习效率。**不要跳过。**

## 前置检查

- [ ] Node.js ≥ 18 已安装（终端执行 `node -v`）
- [ ] VSCode 已安装
- [ ] Chrome 或 Edge 已安装
- [ ] Git 已安装（`git --version`）

如果缺，先补。装不上的把报错贴给智能体。

## T1 · 环境跑通与读代码（4h）

**目标**：`demo1` 能跑起来，并且你能说出「从打开页面到角色能动」的完整链路。

**步骤**
1. 进 `demo1/` 执行 `npm install`，再 `npm run dev`，浏览器打开提示的地址
2. 玩 3 遍，刻意测试边界：走到屏幕外会怎样？星星掉下去会消失吗？能不能卡在平台边缘？
3. 按 `README.md` 的顺序读 4 个文件：`main.ts` → `BootScene.ts` → `MenuScene.ts` → `GameScene.ts`
4. 用纸/笔记画一条链路图：**谁创建了谁，谁在什么时候被调用**
5. 玩的时候的 5 个疑问写下来

**产出**：`demos/s00-setup/NOTES.md`，包含
- 环境信息（node 版本、浏览器版本）
- 链路图（文字或 ASCII 都行）
- 5 个疑问

**验收**
- [ ] `npm run dev` 能跑，改一行代码后浏览器自动更新（验证热更新）
- [ ] 能不看文件说出「入口是哪个文件、它做了什么」
- [ ] NOTES.md 里 5 个疑问都是**具体的**（反面例子：「Phaser 怎么用」；正面例子：「为什么星星会落在地上而不是穿过去」）

**给智能体的提示**：读到 `this.physics.add.existing(platform, true)` 时，问用户「第二个参数 `true` 是什么含义，如果不传会怎样」。这是理解「静态体 vs 动态体」的最佳切入点。不要直接讲答案。

## T2 · 断点调试（4h）

**目标**：会用断点看游戏运行时的真实数据。这是后续所有调试的基础。

**步骤**
1. 打开 DevTools（F12）→ Sources 面板，找到 `GameScene.ts`（Vite 会提供 sourcemap）
2. 在 `update()` 里打断点，观察：它每秒被调用多少次？`delta` 参数是多少？
3. 在断点处看作用域里的 `this.player.body.velocity`，按 F10 单步，观察值的变化
4. 试一次「条件断点」：只在 `this.player.body.velocity.y > 0` 时断住
5. 试一次 `console.time` / `console.timeEnd` 量一段代码耗时
6. 故意制造一个错误（比如把 `this.player` 写成 `this.playr`），看报错信息怎么定位

**产出**：在 `NOTES.md` 追加「调试笔记」：截图或文字记录
- update 的调用频率
- velocity 在跳跃过程中的变化序列
- 一次真实报错的排查过程

**验收**
- [ ] 能说出 `update` 每秒大约被调用多少次，以及为什么是这个数
- [ ] 能用条件断点停住某个特定帧
- [ ] 能看懂调用栈（Call Stack），指出是谁调用了你断点所在的方法
- [ ] 制造的错误能自己定位到行

**给智能体的提示**：用户很可能会说「断点停不下来」。常见原因是代码已经编译过、面板选错了文件（要看 `src/` 下的原始 TS 而不是打包产物）。让他先检查 Sources 里显示的是不是 TS 原文件。

## T3 · Git 基线（4h）

**目标**：有版本管理习惯，敢改代码（因为改坏了能回去）。

**步骤**
1. 在 `D:/GameProject/learning` 根目录初始化仓库（**注意**：不是给 `demo1` 单独建，整个学习目录一个仓库）
2. 检查 `.gitignore`：必须忽略 `node_modules/`、`dist/`、`.DS_Store`、`*.log`
3. 第一次提交：`chore: 初始化学习仓库`
4. 把 `NOTES.md` 提交：`docs: 添加 s00 环境与调试笔记`
5. 做一次「故意破坏再恢复」：改坏一个文件 → `git diff` 看变化 → `git checkout -- <file>` 恢复
6. 学会 3 个命令就够用：`git status`、`git add -p`、`git commit -m`

**验收**
- [ ] `git log --oneline` 有 ≥3 次提交，信息能看懂是在干什么
- [ ] `git status` 显示干净，`node_modules` 不在待提交列表里
- [ ] 做过一次「改坏 → diff → 恢复」，能说清 `git diff` 和 `git status` 的区别
- [ ] 能解释「为什么要小步提交」

**注意**：`demo1/node_modules` 有 2000+ 文件，如果已经误入库，用 `git rm -r --cached node_modules` 修正，不要 `rm -rf`。

## T4 · AI 协作规则与学习节奏（4h）

**目标**：把「怎么用 AI 学」写成自己的规则。这一步看起来虚，但决定了你是「学会」还是「抄完就忘」。

**步骤**
1. 读 `START_HERE.md` 第 3 节，用**自己的话**改写成 5–8 条你认同的规则，写进 `NOTES.md`
2. 设计你的提问模板，至少包含：我卡在哪 / 我试过什么 / 我期望什么 / 给我提示不要给答案
3. 实测一次：拿 T1 里的一个疑问，用你的模板问 AI，看回答质量是否比随便问更好
4. 设计你的每周节奏（20h 怎么排）：
   - 建议 3h/天 × 6 天 + 1 天复盘（复盘日不写新代码，只看笔记、补验收、整理疑问）
   - 每天开始前 5 分钟：读昨天的笔记，写下今天的 1 个目标
5. 决定笔记放哪：`notes/` 下按 Stage 建文件

**产出**：`NOTES.md` 里「我的 AI 协作规则」+「每周时间表」

**验收**
- [ ] 规则是**可执行**的（「多思考」不行，「先自己想 10 分钟再问」可以）
- [ ] 有一条规则是「AI 给完整实现后，我必须合上代码重写一遍」
- [ ] 每周时间表具体到「哪天几点做什么」，且留了缓冲
- [ ] 用模板问过一次，能说出和随便问的差别
