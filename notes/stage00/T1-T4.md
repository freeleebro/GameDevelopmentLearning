# 补充（2026-10-23）· 物理与帧率的三个核心问题

> 起因：三个答不上来的问题——① `add.existing` 第二个参数是什么 ② 星星为什么能停在平台上 ③ 谁把速度变成了位置。
> 答案全部用 Phaser 3.80 源码 `src/physics/arcade/` 核对过，不是凭印象。

## 0. 一条主线：精灵负责显示，物理体负责几何

- **精灵（Sprite）**：屏幕上被画出来的那个东西，有 `x / y / angle / displayWidth`。
- **物理体（Body）**：挂在精灵身上的另一个对象，有自己的 `position / velocity / width / height`，负责算重力、碰撞、分离。

两者每帧同步一次：**帧初 body 从精灵取位置，帧末精灵从 body 取位置**。记住这条，后面所有"为什么改了没反应"都有答案。

## 1. `physics.add.existing(obj, isStatic)` 的第二个参数

源码 `Factory.js` 里就一行判断：

```js
var type = (isStatic) ? CONST.STATIC_BODY : CONST.DYNAMIC_BODY;
```

传 `true` → 静态体；不传 / 传 `false` → 动态体。两者差别：

| | 静态体（`true`） | 动态体（省略/`false`） |
| --- | --- | --- |
| `allowGravity` | `false` | `true` |
| `immovable` | `true` | `false` |
| `moves` | `false` | `true` |
| 每帧积分 | **跳过**（`Body.update` 里 `if (!this.moves) return`） | 执行 |
| 会被别的物体推动 / 撞偏 | 不会 | 会（除非手动 `setImmovable(true)`） |
| 典型用途 | 地板、墙、平台、静态障碍 | 玩家、敌人、子弹、掉落物 |

**不传 `true` 会怎样**（demo1 实际配置 `gravity: { x: 0, y: 400 }`，画布 800×600）：
平台变动态体 → 受重力 400 下落 → 落到画布底部 y≈600 被世界边界拦住 → 玩家站在 y≈553 悬空 → 一起掉，整关报废。

> 口诀：**自己会动的用动态体，不动但需要被撞的用静态体。**

## 2. 星星为什么停在平台上 —— 是 collider，不是世界边界

用坐标就能反证：

| 对象 | 参数 | 关键边 |
| --- | --- | --- |
| 平台 | `add.rectangle(400, 568, 800, 30)` | 中心 y=568，高 30 → **顶面 y≈553** |
| 世界边界 | 画布高 600 | 下沿 **y=600** |

如果只靠世界边界，星星会**穿过平台**一路掉到 y=600 才停——那已经在平台下方 47px、贴着屏幕底边了。但实际看到的是星星稳稳停在平台表面，所以负责停住它的只能是 `collider`。

精确说法：**不加 collider，星星穿过平台落到画布底部；连世界边界也关掉，才真掉出屏幕。**

能让物体停住的东西只有三种：

1. **碰撞体（collider）** —— 主力，负责绝大多数"站住 / 撞墙 / 落地"
2. **世界边界（`collideWorldBounds`）** —— 保险，只管场景四周
3. **手写约束** —— 自己判断条件把速度归零（S05 的手感调优会大量用）

> 最该背下来的一句：**重力只负责加速，永远不会让东西停下来。**

对照实验（2026-10-23 已实测）：
① 注释掉 `physics.add.collider(this.stars, platform)` → 星星穿过平台掉到画布底部；
② 再把星星组的 `collideWorldBounds: true` 改成 `false` → 星星掉出屏幕。

## 3. 谁把速度变成位置 —— 引擎里那三行

`arcade/Body.js` 的 `update(delta)`：

```js
prev.set(pos.x, pos.y);                       // 记下本帧起点

if (!this.moves) {                            // 静态体到这里就返回了
  this._dx = pos.x - prev.x;
  return;
}

this.world.updateMotion(this, delta);          // 重力：velocity.y += (gravity.y) * delta
this.newVelocity.set(vel.x * delta, vel.y * delta);
pos.add(this.newVelocity);                     // position += velocity * delta  ← 位置是这么来的
```

三个关键点：

- `update()` 里**只改速度**，位置是引擎用速度乘上 `delta` 积分出来的；
- 乘的是 `delta`（这一次步长的秒数），**不是固定值**——所以"重力 400"的含义是"每秒给向下速度加 400 px/s"，不是"每帧下移 400 像素"；
- 顺序是"先按重力更新速度，再用**更新后**的速度算位移"，这叫**半隐式欧拉（semi-implicit Euler）**，比显式欧拉稳定，游戏引擎的标准做法。

一帧的完整顺序（`World.update` 里就是这个次序）：

1. **`body.preUpdate(willStep, delta)`**：`resetFlags()` → `updateFromGameObject()`（精灵→body 同步）→ 存 `prev` → 若本帧要步进则 `body.update(delta)` 积分
2. 建碰撞树（`tree.load(bodies)`，空间分区，避免两两全比）
3. 逐个 collider 检测 + **分离（separate）**：把重叠推开、清掉法向速度
4. **`postUpdate`**：把 `body.position` 写回精灵，这一帧才算"看得见"

两个立刻能用的推论：

- 想在 update 里改位置，别直接写 `sprite.x`——帧初会被 body 吸收、之后又被碰撞分离修正，结果不可控。瞬移用 `body.reset(x, y)`。
- **瞬移不能靠"把速度调很大"**：速度大只代表"走得快"，路上遇到 collider 还是会被挡住；而且速度会一直保留，下一帧继续飞。

### 3.1 补一个关键事实：物理步长 ≠ 渲染帧长

之前我默认"物理用渲染帧的 delta"，查源码后发现**不是**。`World` 的构造里有：

```js
this.fps = GetValue(config, 'fps', 60);
this.fixedStep = GetValue(config, 'fixedStep', true);
this._frameTime = 1 / this.fps;          // 1/60 秒
this._frameTimeMS = 1000 * this._frameTime;   // 16.67ms
```

`World.update` 里用累加器判断本帧要不要步进：

```js
this._elapsed += delta;                        // delta = 渲染帧耗时（144Hz 下 ≈6.94ms）
var willStep = (this._elapsed >= msPerFrame);  // 攒够 16.67ms 才步进一次
if (!this.fixedStep) { fixedDelta = delta * 0.001; willStep = true; }  // 关掉固定步长才会用渲染 delta
```

所以在 demo1 里：**渲染 144fps，物理固定 60 步/秒**，平均 2.4 个渲染帧对应 1 次物理步进；`Body.update` 收到的 `delta` 恒为 `1/60 = 0.0167s`。

还有一层要注意：`stepsLastFrame = 1`，**一帧最多步进一次**。所以渲染掉到 30fps 时，物理会"变慢"（每秒只跑 30 步）而不是追帧——这是 Arcade 稳、但会时间变慢的原因。

因此手算跳跃要用**物理步长 16.67ms**（不是 6.94ms）：

| 时刻 | velocity.y | 本次步进位移 |
| --- | --- | --- |
| 起跳那次步进 | `-400` | `-400 × 0.0167 ≈ -6.67px` |
| 下一次步进 | `-400 + 400×0.0167 ≈ -393.3` | `≈ -6.56px` |
| 顶点 | 由负变正的那次步进 | —— |

连续解：上升时间 `v₀/g = 1s`、最高 `v₀²/(2g) = 200px`，即 60 次步进（60Hz 下正好 1 秒）。

**那"帧率越低跳得越高"还成不成立？**

- **变步长（自己写的 `x += v * dt` 循环）**：成立。离散解 `h ≈ v₀²/(2g) + v₀·dt/2`，144Hz ≈ 201.4px、60Hz ≈ 203.3px，差约 2px（1%），可忽略。
- **demo1（Phaser 默认固定步长）**：不成立。`dt` 恒为 1/60，跳跃高度恒为 ≈203.3px，跟你显示器 60Hz 还是 144Hz 无关。

> 这正是 Phaser 替你做的事，也是 S01 要亲手做一遍的东西：把"渲染帧"和"物理步"分开，用累加器连接。

差约 2px（1%）。原因是离散采样会"冲过头"——离散步长越大，越过顶点那一帧残留的速度越大。这也说明**用帧数当时间单位是错的**，所有和时间有关的量都必须乘 `delta`（S01 主线）。

## 4. 自测订正（两处答错 / 答偏的地方）

**① 第 5 题措辞要改**：`pos.add(vel×dt)` 推进的是**本帧**的位移，不是"下一帧的"。用本帧更新后的速度算本帧位移。视觉上看不出变化，是因为精灵位置要到帧末 `postUpdate` 才同步——不是"算的是下一帧"。

**② 第 6 题（瞬移）结论错**：调大速度做不出瞬移。正确做法：

```ts
this.player.body!.reset(x, y);   // 内部：stop() 清零速度 → setPosition → 同步 prev
```

`reset` 一次搞定三件事：精灵与 body 位置对齐、`prev` 同步（不会拉出一条假位移）、速度清零。这才是瞬移该用的 API。

**③ 改错题① 只说对一半**：`setAllowGravity(false)` 只关掉了重力，动态体仍然是 `moves = true, immovable = false` → 玩家站上去能把它推走、撞一下会偏移。静态体是"永远不动 + 每帧跳过积分"（还省性能）。要让动态体真正站稳，得两个都设：`setAllowGravity(false)` + `setImmovable(true)`。

**④ 改错题② 归因错了**：`!` 是 TypeScript 的编译期非空断言，**运行时被完全擦除**，不可能造成抖动。真实原因是两个叠加：

1. 硬编码的 `553` 是**平台顶面**的 y，不是玩家中心。玩家 20×20，静止时中心应在 `563` → 每帧被抬高 10px；
2. `Body.preUpdate` 里有 `updateFromGameObject()`，会把 `sprite.y` 吃进 `body.position` → 抬到 553 → 重力拉回 563 → 再抬 → 抖 10px。

正确写法：落地后**什么都不用写**，collider 已经把速度清掉了。真要强制约束位置，用 `body.reset(x, y)` 而不是直接写 `y`。
