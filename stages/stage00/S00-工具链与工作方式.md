## T2 · 断点调试（4h）

> **2026-10-23 状态：未通过，已出补课单（物理部分）。**
> 详细教程见 `stages/stage00/补课-DevTools与物理链路.md`：第一～八节是调试工具，第九～十一节是物理链路（`add.existing` 第二参数、谁把速度变成位置、星星为什么停住）。
> 通关条件：补课单第十二节 **9 道自测**全部答对 + 笔记里有实测的 `update` 调用频率数据。

**目标**：会用断点看游戏运行时的真实数据，并且知道断点**能**测什么、**不能**测什么。

**步骤**
1. 打开 DevTools（F12）→ Sources 面板，`Ctrl + P` 输入 `GameScene` 打开源文件（不要点进 `node_modules`）
2. 在 `update()` 里打断点，**按 F8 连续继续**（不是 F10），观察每帧 `this.player.body.velocity` 的变化序列
3. 在 Scope 面板展开 `this → player → body → velocity`，或在 Watch 里加 `this.player.body.velocity.y`
4. 试一次「条件断点」：右键行号 → Add conditional breakpoint
5. 用 `console.log` + `performance.now()` 每秒打一次 `update` 执行次数（补课单第五节方法 2）
6. 故意制造一个错误（比如把 `this.player` 写成 `this.playr`），看报错信息怎么定位

**产出**：在 `notes/stage00/T2.md` 追加
- `update` 频率实测数据（跑 10 秒的日志）
- 跳跃全过程 velocity.y 的变化序列
- 一次调用栈的截图/抄录，并标出「哪一行是我的代码、哪一行是引擎」
- 一次真实报错的排查过程
- 第十一节那个「注释掉 collider 看星星掉哪」的实验结果（3 步现象记录）

**验收**
- [ ] 能说出 `update` 每秒大约被调用多少次，**以及自己是用什么方法测出来的**
- [ ] 能用条件断点停住某个特定帧
- [ ] **能读懂调用栈**：指出最上面一行是什么、往下第一行「自己写的函数」是哪个
- [ ] 制造的错误能自己定位到行
- [ ] 能回答：`velocity.y > 0` 是上升还是下落？顶点该怎么判断？

## T3 · Git 基线（4h）

> **2026-10-23 状态：用户要求跳过「学习 Git」，但仓库已实际建好并推送（`github.com/freeleebro/GameDevelopmentLearning`，首次提交 `1237f7c`）→ 判定 ✅。**
> 缺的不是仓库，是「改坏了怎么回滚」的手感。下面是 5 分钟最小版，S01 开始前扫一眼即可。

### 5 分钟最小版（S01 前必须做，否则改坏了没有撤销键）

```bash
cd D:/GameProject/learning
git init
git add -A
git commit -m "chore: 初始化学习仓库"
```

之后每次会话结束只需两步：

```bash
git add -A
git commit -m "S00: 补完 T2 调试笔记"
```

改坏了想回到上次提交：

```bash
git checkout -- <改坏的文件路径>
```

**只记这 4 条命令就够用。** 分支、rebase、stash 这些等你真的需要时再学。

### 完整版（暂缓，S12 发布阶段前补）

**目标**：有版本管理习惯，敢改代码（因为改坏了能回去）。

**步骤**
1. 在 `D:/GameProject/learning` 根目录初始化仓库（**注意**：不是给 `demo1` 单独建，整个学习目录一个仓库）
2. 检查 `.gitignore`：必须忽略 `node_modules/`、`dist/`、`.DS_Store`、`*.log`
3. 第一次提交：`chore: 初始化学习仓库`
4. 把 `NOTES.md` 提交：`docs: 添加 s00 环境与调试笔记`
5. 做一次「故意破坏再恢复」：改坏一个文件 → `git diff` 看变化 → `git checkout -- <file>` 恢复
6. 学会 3 个命令就够用：`git status`、`git add -p`、`git commit -m`

**验收**
- [ ] `git log --oneline` 有 ≥3 次提交，信息能看懂是在干什么
- [ ] `git status` 显示干净，`node_modules` 不在待提交列表里
- [ ] 做过一次「改坏 → diff → 恢复」，能说清 `git diff` 和 `git status` 的区别
- [ ] 能解释「为什么要小步提交」

**注意**：`demo1/node_modules` 有 2000+ 文件，如果已经误入库，用 `git rm -r --cached node_modules` 修正，不要 `rm -rf`。

## T4 · AI 协作规则与学习节奏（4h）

**目标**：把「怎么用 AI 学」写成自己的规则。这一步看起来虚，但决定了你是「学会」还是「抄完就忘」。

**步骤**
1. 读 `START_HERE.md` 第 3 节，用**自己的话**改写成 5–8 条你认同的规则，写进 `NOTES.md`
2. 设计你的提问模板，至少包含：我卡在哪 / 我试过什么 / 我期望什么 / 给我提示不要给答案
3. 实测一次：拿 T1 里的一个疑问，用你的模板问 AI，看回答质量是否比随便问更好
4. 设计你的每周节奏（20h 怎么排）：
   - 建议 3h/天 × 6 天 + 1 天复盘（复盘日不写新代码，只看笔记、补验收、整理疑问）
   - 每天开始前 5 分钟：读昨天的笔记，写下今天的 1 个目标
5. 决定笔记放哪：`notes/` 下按 Stage 建文件

**产出**：`NOTES.md` 里「我的 AI 协作规则」+「每周时间表」

**验收**
- [ ] 规则是**可执行**的（「多思考」不行，「先自己想 10 分钟再问」可以）
- [ ] 有一条规则是「AI 给完整实现后，我必须合上代码重写一遍」
- [ ] 每周时间表具体到「哪天几点做什么」，且留了缓冲
- [ ] 用模板问过一次，能说出和随便问的差别
