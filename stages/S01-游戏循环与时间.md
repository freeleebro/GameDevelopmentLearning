# S01 · 游戏循环与时间（24h / 约 6 天）

> **这是整个计划里最重要的 Stage。**  
> 游戏开发与普通软件开发最本质的区别就在这 300 行里。手写过一次，Unity 的 `Update` / `FixedUpdate` / `Time.deltaTime` 你永远不会用错。
>
> **硬性约束**：本 Stage **不允许使用 Phaser**。只用原生 `canvas` + `requestAnimationFrame`。

## 目录约定

```
demos/s01-loop/
├── index.html          # 只有一个 <canvas>
├── package.json        # 用 vite，和 demo1 一样
├── tsconfig.json
└── src/
    ├── main.ts         # 入口：创建循环
    ├── loop.ts         # 循环本身（核心，会被你反复改）
    ├── world.ts        # 世界状态（方块、重力）
    └── render.ts       # 绘制
```

**为什么要分层**：`loop.ts` 不知道方块是什么，`world.ts` 不知道 canvas 是什么。这是后面所有架构讨论的起点。

## T1 · 最小可运行的循环（3h）

**目标**：一个方块在动，而且你能说清「它为什么在动」。

**要写的**

2. 一个 `while`-式循环的等价物：`requestAnimationFrame` 递归调用
3. 清屏 → 更新位置 → 绘制，三步的顺序是什么

**关键问题（自己回答，写进笔记）**

- 如果不 `clearRect`，会发生什么？

**验收**

- [ ] 方块在动，屏幕不拖影
- [ ] 能说出 rAF 一帧的完整流程

**给智能体的提示**：如果用户写成了 `setInterval(update, 16)`，不要直接否定，让他跑起来后把浏览器标签切到后台再切回来，观察「暂停后位置跳变」——这是最好的教材。

## T2 · 帧率无关（4h）

**目标**：同一个物体，在 30 / 60 / 144 帧下走过同样的距离。

**要写的**

1. 把「每帧加固定值」改成「按时间加」（`x += speed * dt`）
2. `dt` 从哪来：`performance.now()` 差值，**单位统一成秒**
3. 加一个调试面板：显示当前 FPS、上一帧 `dt`、物体 x 坐标
4. **做一个强制帧率开关**：按键 1/2/3 分别把 `dt` 钳制成 1/30、1/60、1/144（用于测试，不改真实 rAF）

**必做实验（记录数据）**

| 帧率    | 理论耗时 | 实测耗时 | 误差 |
| ----- | ---- | ---- | -- |
| 1/30  | —    | —    | —  |
| 1/60  | —    | —    | —  |
| 1/144 | —    | —    | —  |

**验收**

- [ ] 三种帧率下耗时差异 < 2%
- [ ] 能解释 `x += 5` 为什么是错的（说出「速度」和「每帧位移」的区别）
- [ ] 能解释 `dt` 用毫秒会出什么 bug
- [ ] 数据表是实测的，不是编的

**给智能体的提示**：常见错误是 `dt` 一直是 0.016（写死）或没除以 1000。让他把 `dt` 打到屏幕上盯 10 秒就能发现。

## T3 · 掉帧、卡顿与时间钳制（3h）

**目标**：卡一下不会让物体瞬移穿墙。

**要写的**

1. 做一个「人为卡顿」开关：按住某键时主线程阻塞 300ms（用忙等，故意制造掉帧）
2. 观察未钳制时物体跳多远
3. 加入 `dt = Math.min(dt, MAX_DT)`（比如 0.1s），再观察
4. 思考：钳制会带来什么副作用？（时间变慢，但对玩家来说比穿墙好）

**验收**

- [ ] 能演示「未钳制 → 穿墙 / 钳制 → 不穿墙」的对比
- [ ] 能说出为什么钳制上限一般取 0.1–0.25 秒
- [ ] 能说出「切到后台再回来」时 `dt` 会异常大，以及怎么处理

**给智能体的提示**：这是理解后面「Unity 里切场景/加载时为什么会穿模」的伏笔。

## T4 · 固定步长 + 累加器 + 插值（6h，本 Stage 最难）

**目标**：物理以固定频率推进（不管渲染多少帧），渲染用插值让画面平滑。

**要写的**

1. 把 `world.update(dt)` 拆成两层：
   - `fixedUpdate(FIXED_DT)`：物理，一秒固定跑 60 次
   - `render(alpha)`：绘制
2. 用**累加器**（accumulator）模式：把真实时间存起来，够一个固定步长就跑一次物理
3. 加 `alpha = accumulator / FIXED_DT`，在渲染时把「上一帧位置」和「当前帧位置」插值
4. 键盘控制：按 F 切换「固定步长」/「变步长」两种模式，肉眼/数据对比

**验收**

- [ ] 固定步长模式下，即使在 144Hz 屏幕上，物理仍然是每秒 60 次（用计数器证明）
- [ ] 有/无插值两种情况，在 144Hz 下肉眼可见差异（无插值会抖）
- [ ] 能画出「真实时间 → 累加器 → 物理步数 → alpha」的关系图
- [ ] 能说清「为什么不干脆全用固定步长渲染」

**给智能体提示**：这是唯一一个允许直接讲原理的环节（因为累加器模式自己顿悟概率低）。但**代码仍要用户写**，最多给这段伪代码：

```
accumulator += frameTime
while (accumulator >= FIXED_DT) {
    prev = curr
    fixedUpdate(FIXED_DT)
    accumulator -= FIXED_DT
}
alpha = accumulator / FIXED_DT
render(lerp(prev, curr, alpha))
```

## T5 · 更新顺序、暂停与时间缩放（4h）

**目标**：暂停是真的暂停；慢动作不会让逻辑错乱。

**要写的**

1. 明确并实现这个顺序：`读输入 → 逻辑更新 → 物理步进 → 渲染`
2. 按 P 暂停：物理和逻辑都不推进，但渲染继续（画面不黑）
3. 暂停恢复后**不能**出现时间跳跃（累加器要处理）
4. 加时间缩放：按 `[` `]` 把游戏速度调到 0.25× / 1× / 2×（用于做慢动作演出）
5. 加一个「帧序号」显示，暂停时它应该停止增长

**验收**

- [ ] 暂停时帧序号停止、物体静止、画面不黑
- [ ] 暂停 10 秒后恢复，物体不会突然前进一大段
- [ ] 0.25× 速度下，跳跃轨迹形状不变、只是变慢（说明物理是按固定步长跑）
- [ ] 能解释「暂停应该暂停时间，还是暂停更新」的区别
